# Data Warehousing for Data Engineering

## 1. Introduction

Data warehousing is a core part of data engineering because it converts data from operational and external systems into reliable analytical datasets.

A data engineer designs pipelines that move data from sources into analytical storage.

```text
Sources
 |
 v
Ingestion
 |
 v
Raw / Staging
 |
 v
Transformation
 |
 v
Data Warehouse
 |
 v
Data Marts
 |
 v
BI / Analytics
```

## 2. Role of a Data Engineer

A data engineer commonly works on:

- Data ingestion
- ETL / ELT
- Data modeling
- Data quality
- Warehouse design
- Pipeline orchestration
- Performance
- Security
- Monitoring

## 3. Operational vs Analytical Systems

Operational systems support transactions.

```text
INSERT
UPDATE
DELETE
```

Analytical systems support:

```text
SELECT
GROUP BY
JOIN
AGGREGATION
```

## 4. OLTP

OLTP means Online Transaction Processing.

Examples:

- Banking transactions
- Orders
- Customer registration
- Vehicle service booking

OLTP systems are optimized for transactions.

## 5. OLAP

OLAP means Online Analytical Processing.

Examples:

- Revenue analysis
- Customer analysis
- Monthly sales
- Vehicle performance analytics

OLAP systems are optimized for analytical queries.

Typical workflow:

```text

 |
 v

 |
 v

 |
 v

 |
 v

 |
 v

 |
 v
```

## 7. ETL

ETL means:

```text
Extract
Transform
Load
```

Data is transformed before being loaded into the target warehouse.

## 8. ELT

ELT means:

```text
Extract
Load
Transform
```

Modern cloud warehouses often support ELT because transformation can occur using warehouse compute.

## 9. Source Systems

Sources can include:

- PostgreSQL
- MySQL
- MongoDB
- APIs
- CSV
- JSON
- Kafka
- IoT devices

## 10. Staging Layer

The staging layer receives extracted data.

```text
Source
 |
 v
Staging
 |
 v
Warehouse
```

Staging can help isolate source extraction from transformations.

## 11. Raw Layer

A raw layer preserves source-like data.

```text
raw/
 |
 +-- customers
 +-- orders
 +-- vehicles
```

Raw data can help with replay and troubleshooting.

## 12. Cleaned Layer

The cleaned layer standardizes data.

Operations:

- Type conversion
- Deduplication
- Null handling
- Validation
- Standard naming

## 13. Curated Layer

Curated data is business-ready.

Example:

```text
Raw Sales
 |
 v
Clean Sales
 |
 v
Monthly Revenue
```

## 14. Dimensional Modeling

A data engineer often models analytics using:

- Fact tables
- Dimension tables

## 15. Fact Table

A fact table stores measurable business events.

Example:

```text
fact_sales

sale_key
customer_key
vehicle_key
date_key
dealer_key
quantity
amount
```

## 16. Dimension Table

A dimension stores descriptive information.

Example:

```text
dim_vehicle

vehicle_key
model
brand
fuel_type
year
```

## 17. Star Schema

```text
           dim_customer
                |
dim_vehicle -- fact_sales -- dim_date
                |
           dim_dealer
```

The fact table is at the center.

## 18. Grain

Grain defines what one fact row represents.

Example:

```text
One row = One vehicle sale
```

Grain must be decided before adding measures.

## 19. Surrogate Keys

Warehouse dimensions often use surrogate keys.

Example:

```text
customer_key = 1001
```

The source system may use:

```text
customer_id = C001
```

## 20. Slowly Changing Dimensions

Dimensions can change over time.

Example:

```text
Customer City:
Rajkot
   |
   v
Ahmedabad
```

The warehouse must decide how history is handled.

## 21. SCD Type 1

Type 1 overwrites old values.

```text
Rajkot
   |
   v
Ahmedabad
```

History is not retained.

## 22. SCD Type 2

Type 2 preserves history.

```text
Customer
 |
 +-- Rajkot     2025-2026
 |
 +-- Ahmedabad  2026-
```

Common columns:

```text
effective_from
effective_to
is_current
```

## 23. Data Quality

A warehouse should validate:

- Completeness
- Accuracy
- Consistency
- Uniqueness
- Timeliness
- Validity

## 24. Data Quality Example

Sales amount should not be negative unless the business explicitly allows refunds or adjustments.

```sql
SELECT *
FROM sales
WHERE amount < 0;
```

## 25. Deduplication

Duplicate records can distort metrics.

Example:

```text
S001
S001
```

Use business keys or event IDs to identify duplicates.

## 26. Null Handling

Nulls should have defined business meaning.

Possible meanings:

- Unknown
- Not applicable
- Missing
- Not collected

Do not blindly replace every null with zero.

## 28. Incremental Processing

Instead of processing everything:

```text
10 TB
```

process only:

```text
Today's 50 GB
```

when the source and business requirements allow it.

```text

 |
 v

```

CDC is useful for near-real-time warehouse loading.

Example:


## 57. Best Practices

- Define grain
- Use consistent naming
- Build incremental pipelines
- Test transformations
- Monitor freshness
- Secure sensitive data
- Document models
- Optimize expensive queries

## 58. Common Mistakes

Avoid:

- No defined grain
- Duplicate facts
- Uncontrolled schema changes
- Full refresh everywhere
- No quality checks
- No lineage
- No monitoring
- Poor naming
